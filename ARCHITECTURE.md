# Архитектура: Анти-галлюцинатор, часть I

Домашка 3 по ТИ (см. [TCS_2026_hw3.pdf](TCS_2026_hw3.pdf)). Язык реализации — Python.
Модели: **DeepSeek**, **Qwen**, **ChatGPT (GPT-6 / OpenAI API)**.

## 1. Общая идея пайплайна

```
testcases.py (5 фиксированных описаний)
        │
        ▼
PromptBuilder ──► LLMClient (DeepSeek | Qwen | OpenAI) ──► сырой текстовый ответ
        │                                                              │
        │                                                    сохраняем как есть в файл
        ▼                                                              │
   (повтор ×50 на каждую пару модель×тесткейс)                         ▼
                                                              data/raw/<model>/<testcase>/run_XXX.txt
                                                                        │
                                                                        ▼
                                                              AutomatonParser (строгий парсинг)
                                                                        │
                                     ┌──────────────────────────────────┼───────────────────────────┐
                                     ▼                                  ▼                            ▼
                          FormatValidator (3 балла)            Simulator + ground truth (5)   NFA→DFA (7 баллов)
                                     │                                  │                            │
                                     └──────────────────┬───────────────┴────────────┬───────────────┘
                                                         ▼                            ▼
                                                 RunResult (per-run metrics, сериализуется в JSON/CSV)
                                                         │
                                                         ▼
                                              MetricsAggregator → final_table.md/.csv + выводы
```

Каждый прогон (`model × testcase × run_id`) проходит все три проверки независимо — так одна ошибка (например, невалидный формат) не блокирует остальные метрики, а просто помечается как `N/A`.

## 3. Ключевые сущности

### 3.1 `Automaton` (src/automaton/model.py)
```python
@dataclass
class Automaton:
    n: int                                   # число состояний
    m: int                                   # размер алфавита
    starts: set[int]
    finals: set[int]
    transitions: dict[tuple[int, int], set[int]]   # (state, symbol_idx) -> {state, ...}
```
Трактуем как NFA с несколькими стартовыми состояниями (без ε-переходов — формат их не предусматривает).

### 3.2 Тесткейсы (src/testcases.py)
Для каждого из 5 ID (`basic`, `4th-symbol`, `employer`, `intersection`, `personal`) храним:
- `description: str` — ровно текст из таблички (для intersection — с TeX-значками), который уходит в промпт;
- `alphabet: tuple[str, ...]` — фиксированный порядок символов, который сообщаем модели (индекс символа в этом кортеже = номер, который модель обязана использовать в переходах);
- `ground_truth: Callable[[str], bool]` — эталонный предикат принадлежности языку, написанный руками (не через автомат — так проще и надёжнее для `intersection`, где иначе пришлось бы отдельно реализовывать reverse+произведение);
- `sample_strings() -> list[tuple[str, bool]]` — набор строк с ожидаемым вердиктом (позитивные/негативные), используется симулятором.

### 3.3 LLMClient
Общий интерфейс `generate(prompt: str) -> str`. Все три модели — ChatGPT, DeepSeek и Qwen —
имеют OpenAI-совместимый REST (`/chat/completions` + Bearer-токен), поэтому у них общая
реализация `OpenAICompatibleClient`, а `openai_client.py`/`deepseek_client.py`/`qwen_client.py`
— это тонкие обёртки только с своим `base_url` (изначально выбирали GigaChat вместо Qwen, но
отказались от него: там ещё и OAuth2 client-credentials, и самоподписанный сертификат
Минцифры для TLS — заметно больше кода и точек отказа ради третьей модели).

Retry с экспоненциальной паузой на 429/5xx, таймаут на запрос. Ответ сохраняется в `data/raw/...` **до** парсинга — если парсинг упадёт, сырой текст всё равно останется на диске для отладки и для сдачи.

### 3.4 FormatValidator (3 балла)
Проверяет то, что не проверяет уже сам parser по построению:
- `n, m` — положительные целые;
- стартовые/конечные состояния — целые из `[0, n)`, без дублей;
- каждая строка перехода — валидный символ `[0, m)` и валидные state-индексы `[0, n)`;
- отсутствие "битых" строк (не то количество токенов, не числа и т.д.).
Возвращает `(is_valid: bool, violations: list[str])` — список конкретных причин идёт в лог, а не только булево значение, это нужно для итоговых "глубокомысленных выводов" (какие именно ошибки типичны для какой модели).

### 3.5 Simulator + проверка корректности (5 баллов)
`simulate(automaton, word) -> bool` — BFS/DFS по множеству активных состояний (стандартный NFA run без ε).
`check_correctness(automaton, testcase) -> bool`:
1. берёт `testcase.sample_strings()`;
2. сравнивает `simulate(automaton, s)` с ground truth для каждой строки;
3. автомат считается корректным, если совпадения 100% (порог — открытое решение, см. §5).

### 3.6 NFA → DFA (7 баллов)
Классическое построение подмножеств, но **лениво**: очередь начинается с множества стартовых состояний, на каждом шаге для текущего подмножества и каждого символа считаем достижимое подмножество и добавляем в очередь, если оно ещё не встречалось (dedup по `frozenset`). Никакого предварительного перебора всех `2^n` подмножеств. Возвращаем `len(visited_subsets)`.

## 4. Метрики и итоговая таблица

`RunResult` (одна запись на прогон):
```
model, testcase, run_id,
is_format_valid, format_violations,
is_input_deterministic,      # сырой автомат уже DFA?
dfa_state_count,              # после determinize()
is_simulation_correct,
latency_ms, raw_file_path
```
Пишется построчно в `data/results/runs.jsonl` — это позволяет пересчитывать метрики и добавлять новые проверки без повторных (платных) запросов к API.

`MetricsAggregator` группирует по `(testcase, model)` и считает ровно те 4 колонки из таблицы в п.3 ПДФ:
- % корректных по формату,
- % детерминированных (по сырому автомату),
- среднее число состояний в DFA,
- % корректных по симуляции,

плюс строку `Всего` (агрегат по всем тесткейсам). Рендерится в Markdown-таблицу (`reports/final_table.md`), куда потом руками дописываются выводы.

## 5. Открытые решения (зафиксировать перед кодом)

Это моменты, где в ПДФ нет однозначного ответа — лучше явно решить и одной строкой описать в отчёте:
1. **Порог "корректности по симуляции"** — 100% совпадений на sample-строках, или допускаем небольшой % ошибок? Предлагаю 100%, но количество sample-строк должно быть достаточным (≥15–20 на тесткейс, позитивные+негативные+граничные).
2. **DFA без sink-состояния** — если для какого-то (state, symbol) нет перехода, не добавляем "мёртвое" состояние-приёмник, иначе среднее число состояний в DFA будет искусственно раздуто и несравнимо между моделями с разной "полнотой" автомата.
3. **`personal`-кейс** — придумать и зафиксировать формулировку в `testcases.py` до первого запуска (одна и та же формулировка должна уйти во все 50 запросов на модель).
4. **Промпт** — единый шаблон для всех моделей (иначе сравнение некорректно): описание формата + один few-shot пример из ПДФ + описание тесткейса, без модель-специфичных подсказок.

## 6. Порядок реализации (инкрементально, по баллам из ПДФ)

1. `automaton/model.py` + `automaton/parser.py` + `automaton/validator.py` + тесты на фикстурах из ПДФ → закрывает 3 балла.
2. `automaton/simulator.py` + `testcases.py` (ground truth + sample_strings) + тесты → закрывает 5 баллов.
3. `automaton/determinize.py` + тесты → закрывает 7 баллов.
4. `llm_clients/*` + `prompt_builder.py` + `pipeline/runner.py` — реальные запросы к трём API, по 50 на тесткейс.
5. `pipeline/evaluator.py` + `metrics/aggregate.py` + `metrics/report.py` — итоговая таблица.
6. Ручной анализ таблицы → выводы в `reports/final_table.md`.

Так части 1–3 (весь "движок") можно полностью написать и протестировать без единого обращения к платным API, а на API-часть тратить время только когда логика уже проверена на ручных примерах.
